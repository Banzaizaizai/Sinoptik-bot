# Спецификация проекта: Telegram-бот погоды для Дрогобича

## 1. Цель

Скрипт/бот, который **2 раза в сутки**:
1. заходит на `https://sinoptik.ua/pohoda/drohobych`,
2. забирает прогноз погоды **на завтра** с разбивкой по времени суток,
3. форматирует его в читабельное сообщение,
4. публикует сообщение в заданный Telegram-канал.

Работает без участия пользователя (полностью автоматически), по расписанию.

---

## 2. Источник данных — что реально отдаёт sinoptik.ua

Проверено вручную (28.08.2026):

- Страница **рендерится на сервере** (нужные данные есть в обычном HTML, отдельного JSON/API-эндпоинта в сетевых запросах не обнаружено — только рекламная телеметрия на `/stats/...`). Значит, для парсинга **не обязателен headless-браузер** — достаточно обычного HTTP GET + разбор HTML. Playwright/Selenium держим как запасной вариант, если верстка окажется JS-зависимой на проде.
- Прогноз на конкретный день доступен по отдельному URL, например:
  - сегодня: `/pohoda/drohobych`
  - на "субботу": `/pohoda/drohobych/subota`
  - на "неделю": `/pohoda/drohobych` (там же таб-бар с 7 днями)
  
  У каждого дня в верхнем таб-баре (навигация по 7 дням) есть прямая ссылка вида `href="/pohoda/drohobych/<slug>"`, где `<slug>` — транслитерация укр. названия дня недели (`subota`, `nedilya`, `ponedilok`, `vivtorok`, `sereda`, `chetver`, вероятно `pyatnytsya`).

  **Важно:** slug для дня недели жёстко не хардкодим. Надёжнее — распарсить таб-бар (7 пунктов меню с датами) на главной странице `/pohoda/drohobych`, найти пункт, где дата = "завтра" (сегодня+1 день), и взять его `href`. Это устойчиво к любым изменениям нумерации/названий и не ломается на стыке недели.

- **⚠️ Ключевое расхождение с ТЗ: данные НЕ почасовые.** Таблица на сайте даёт значения с шагом **3 часа**: `0:00, 3:00, 6:00, 9:00, 12:00, 15:00, 18:00, 21:00` (8 точек в сутки, сгруппированных по блокам ніч/ранок/день/вечір). Настоящего почасового (24 точки) прогноза на этой странице sinoptik.ua нет.

  Варианты:
  - **(рекомендуется)** Принять 3-часовой шаг как факт и в боте/канале называть это "прогноз по интервалам", а не "почасовой" — не вводить подписчиков в заблуждение.
  - Если реально нужен шаг в 1 час — сайт не подходит как источник, нужен другой (например, Open-Meteo, OpenWeatherMap, WeatherAPI — все дают honest hourly через официальный бесплатный API, без скрапинга и без риска бана). Это стоит обсудить отдельно, т.к. меняет источник данных целиком.

- Для каждого 3-часового слота на странице есть строки:
  - температура, °C
  - ощущается как, °C
  - давление, мм рт. ст.
  - влажность, %
  - ветер, м/с (+ вероятно направление — уточняется при разработке, иконки на странице рендерятся не как `<img>`/`<svg>` с понятным `alt`, нужен точечный разбор верстки)
  - вероятность осадков, %
- Плюс текстовое описание дня одним абзацем ("з ранку хмарно, у другій половині дня дощ...") — хороший источник для человекочитаемой сводки/эмодзи.
- Восход/закат, мин./макс. за день — тоже доступны и полезны для шапки сообщения.

### robots.txt
`/pohoda/*` не входит в списки `Disallow` для `User-agent: *` (закрыты только `/api/`, `/stats/`, `/rss/` и служебные пути). Обращение 2 раза в сутки — пренебрежимо низкая нагрузка, этических/технических противоречий с robots.txt нет. Тем не менее:
- ставим осмысленный `User-Agent` (не маскируемся под браузер обманным образом сверх необходимого для рендера),
- не увеличиваем частоту опроса,
- держим таймаут и graceful-обработку 403/429/капчи — сайт коммерческий, доступность/структура могут меняться без предупреждения.

## 4. Архитектура

```
┌─────────────┐     ┌───────────┐     ┌──────────────┐     ┌───────────────┐
│  Scheduler   │────▶│  Fetcher  │────▶│    Parser     │────▶│   Formatter    │
│ (2x/сутки)   │     │ (HTTP GET)│     │ (HTML→модель) │     │ (модель→текст) │
└─────────────┘     └───────────┘     └──────────────┘     └───────┬────────┘
                                                                     │
                                                                     ▼
                                                            ┌────────────────┐
                                                            │ Telegram Sender │
                                                            │ (Bot API)       │
                                                            └────────────────┘
                    Сквозные: Config/Secrets · Logging · Error handling/Retry · Alerting
```

Компоненты — отдельные модули с чёткими границами, чтобы:
- при изменении вёрстки сайта чинить только `Parser`;
- при смене источника данных (см. п.2) заменить `Fetcher`+`Parser`, не трогая остальное;
- покрыть `Parser` и `Formatter` юнит-тестами на сохранённых HTML-фикстурах, без похода в сеть.

## 5. Технологический стек

- **Python 3.11+**
- `httpx` или `requests` — HTTP-запросы (с таймаутом и retry)
- `beautifulsoup4` (+ `lxml`) — разбор HTML
- Отправка в Telegram — простой `POST` на `https://api.telegram.org/bot<token>/sendMessage` через `requests`; отдельная библиотека (`python-telegram-bot`) не нужна, т.к. бот **только отправляет**, не принимает команд.
- `tenacity` — retry с экспоненциальной задержкой на сетевые сбои
- Планирование запуска — **не** держим вечный процесс с внутренним scheduler'ом по умолчанию; см. п.9 (проще и надёжнее — системный планировщик).
- Конфиг — `.env` (`python-dotenv`) или `config.yaml`, секреты не коммитим.

## 6. Расписание

Два запуска в сутки, время по Europe/Kyiv (у Дрогобича тот же часовой пояс):

- **08:00** — утренний прогноз на завтра (для тех, кто планирует день заранее)
- **20:00** — вечерний прогноз на завтра (обновлённые, более точные данные ближе к дате)

*(Открытый вопрос — см. п.15: подтвердить время с пользователем, оно легко настраивается.)*

## 8. Конфигурация и секреты

Через переменные окружения / `.env`, не в коде и не в git:
- `TELEGRAM_BOT_TOKEN`
- `TELEGRAM_CHANNEL_ID` (например `@drohobych_weather` или числовой `-100...`)
- `CITY_URL_SLUG=drohobych`
- `TIMEZONE=Europe/Kyiv`
- `SEND_TIMES=08:00,20:00` (если планирование делает сам процесс, а не ОС)

Бот должен быть добавлен в канал **администратором** с правом публикации сообщений — это разовая ручная настройка пользователем в Telegram, вне зоны ответственности скрипта.

## 9. Развёртывание и планирование запуска

Т.к. рабочая машина — Windows, два реалистичных варианта:

**Вариант A (рекомендуется для старта): Windows Task Scheduler**
- Скрипт — обычный однократный запуск (fetch → parse → send → exit), без внутреннего цикла.
- Планировщик Windows дергает его в 08:00 и 20:00.
- Плюсы: просто, не требует постоянно работающего процесса, встроенные логи/повторы средствами ОС.

**Вариант B: Docker-контейнер с cron/`schedule`-циклом внутри**
- Полезно, если позже переносим на VPS/сервер (Linux), для единообразия окружения.
- Тот же скрипт, обёрнутый в `cron` внутри контейнера или бесконечный цикл с `schedule`/`APScheduler`.

Оба варианта используют один и тот же "ядровый" скрипт (fetch-parse-format-send) — выбор планировщика не влияет на архитектуру из п.4.

## 10. Обработка ошибок и отказоустойчивость

- Таймауты на HTTP-запрос (например 15 сек) + до 3 повторов с backoff при сетевых ошибках/5xx.
- Если структура HTML изменилась и парсинг не удался — **не отправлять в канал мусор/пустое сообщение**. Вместо этого:
  - залогировать ошибку с деталями (что именно не найдено),
  - опционально отправить алерт **пользователю в личку** (отдельный `ADMIN_CHAT_ID`), а не в публичный канал.
- Если Telegram API вернул ошибку (rate limit, неверный chat_id и т.п.) — залогировать и не падать молча.
- Идемпотентность не критична (нет БД/дедупликации) — просто публикация нового сообщения дважды в день, это ожидаемое поведение.

## 11. Логирование

- Стандартный `logging` в файл (ротация, например `RotatingFileHandler`) + вывод в stdout (виден в Task Scheduler/Docker logs).
- Логировать: время запуска, URL запроса, HTTP-статус, успех/неуспех парсинга, факт отправки в Telegram (message_id).

## 12. Тестирование

- Юнит-тесты `Parser`: сохранить 1–2 реальных HTML-снапшота страницы как фикстуры, проверять, что модель `ForecastDay` собирается корректно.
- Юнит-тесты `Formatter`: модель → ожидаемый текст.
- Интеграционный smoke-test отправки в Telegram — на тестовый приватный чат, не в боевой канал.
- Ручная проверка раз в какое-то время: не изменилась ли верстка сайта (визуально сверить пример вывода с реальной страницей).

## 13. Юридический/этический аспект

- `/pohoda/*` не запрещён в `robots.txt`, частота обращения минимальна (2/сутки) — риск блокировки низкий, но не нулевой (коммерческий сайт может менять политику/добавлять защиту от ботов в любой момент).
- Бот делает **некоммерческую агрегацию публично доступных данных для небольшого канала**, без обхода платного контента/капчи/авторизации. Рекомендуется указывать источник в каждом сообщении (уже заложено в шаблоне, п.7).
- Если в будущем возникнут проблемы с доступом (капча, бан по IP/UA) — не пытаться их обходить агрессивно (это уже вне рамок этого бота), а переходить на официальный weather API (см. п.2).

## 14. Этапы разработки (предложение)

1. Fetcher + Parser для одного дня, локальный прогон, вывод модели в консоль.
2. Логика выбора "завтра" через таб-бар (устойчивая к смене дня недели).
3. Formatter → готовый текст сообщения.
4. Telegram Sender + ручной тест в приватный чат.
5. Логирование, retry, обработка ошибок.
6. Настройка планировщика (Task Scheduler) на 08:00 и 20:00.
7. Прогон "в бою" несколько дней, сверка с реальной страницей, донастройка формата.

## 15. Открытые вопросы к пользователю

1. **"Почасовые" данные** — устраивает ли 3-часовой шаг (реально доступный на sinoptik.ua), или нужен настоящий hourly-прогноз через другой источник (Open-Meteo/OpenWeatherMap, официальный API)?
2. Время двух ежедневных запусков — подходят ли **08:00 и 20:00** (Europe/Kyiv), или нужны другие?
3. Telegram-канал: уже создан? Нужен `@username` или числовой `chat_id`, и бот должен быть добавлен туда администратором с правом постить.
4. Нужен ли параллельно личный чат-алерт админу при сбоях (п.10), или ошибки достаточно смотреть в логах?
5. Где в итоге бот будет постоянно жить: эта Windows-машина (Task Scheduler) или сервер/VPS (Docker)?
